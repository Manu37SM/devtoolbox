### Added (Phase 3 — security/production-readiness pass)

A leaked derived key now only exposes one user's history.

### Fixed (Phase 3 verification — env loading, CORS, build)

Found during the user's real `npm install`/`typecheck`/`test`/`build`/`db:migrate:dev` verification pass, not part of the original Phase 3 wave 1 scope:

- **`OptionalJwtAuthGuard.handleRequest` didn't match `IAuthGuard`'s generic signature** (`<TUser>`) — typecheck error. Fixed to a generic `handleRequest<TUser>(...): TUser`.
- **`api-client.ts` silently dropped the `Authorization` header** — `rawRequest`'s header merge did `{ ...init.headers }`, and object-spreading a `Headers` instance (which `request()` builds to attach the token) copies nothing, since `Headers` doesn't expose its entries as own enumerable properties. Fixed to merge through the `Headers` API consistently.
- **Prisma `Json`-field type mismatches** in the new Pipelines/Share services — Zod validates `optionsJson`/`payload` as `Record<string, unknown>`, but Prisma's generated create/update input type is the stricter `Prisma.InputJsonValue`. Fixed with an explicit, documented cast (`toInputJson` helper in `pipelines.service.ts`, inline in `share.service.ts`) rather than loosening the Zod schema.
- **Root `.env` wasn't reaching either workspace.** Prisma's CLI and Next.js both only look for `.env` inside their own workspace directory (`backend/`, `frontend/`), not the monorepo root — so `prisma migrate dev` failed with "Environment variable not found: DATABASE_URL" and the running apps would have silently missed every var in the root `.env` too. Fixed by wrapping `dev`/`build`/`start`/`db:*` scripts in both workspaces with `dotenv-cli` (`dotenv -e ../.env -- ...`), keeping the single root `.env` as the actual source of truth. Also added the missing root-level `db:migrate:dev` proxy script (only `db:migrate` existed).
- **`next build` failed with a confusing `<Html> should not be imported outside of pages/_document` error** — root cause was `NODE_ENV=development` from `.env` leaking into the `dotenv`-wrapped `build`/`start` scripts (Next warns about this as a "non-standard NODE_ENV value" and behaves inconsistently during static generation). Fixed by adding `cross-env NODE_ENV=production` ahead of the `dotenv` call in `build`/`start` for both workspaces — `dotenv` never overrides an already-set variable, so this pins production commands to the right mode regardless of what `.env` says (which is correctly `development`, for `dev`).
- **CORS anti-pattern in `main.ts`** (reflecting any request origin with `credentials: true`, effectively disabling CORS protection for cookie-authenticated requests) — pre-existing from earlier scaffolding, but only became a real risk once this wave introduced the first credentialed cookie (the refresh token). Fixed to pin against `FRONTEND_URL`.
- **Docker Postgres port conflict**: `docker-compose.yml`'s Postgres was mapped to the host's default 5432, which collided with a natively-installed Postgres on the dev machine — connections landed on whichever service Windows/Docker Desktop happened to route them to, producing intermittent/misleading `P1000` auth failures even with correct credentials. Remapped to host port 5433; `.env.example`'s `DATABASE_URL` updated to match.
- **Frontend dev/start server silently bound to port 4000 instead of 3000, colliding with the backend.** `.env`'s `PORT=4000` is meant only for the backend (`ConfigModule`/`main.ts` read it), but Next.js's own dev/start server *also* honors a `PORT` env var for its own listen port — once the frontend's scripts started loading the whole root `.env` via `dotenv`, it inherited `PORT=4000` too, so frontend and backend raced for the same port (`EADDRINUSE` for whichever lost). Fixed by pinning the frontend explicitly with `next dev -p 3000`/`next start -p 3000`, which overrides any inherited `PORT`.

### Added (Phase 3 — frontend polish)

- **OAuth "Continue with GitHub/Google" buttons** on `/login` and `/register` (new `components/auth/OAuthButtons.tsx`), plus a `/auth/callback/[provider]` page that completes the exchange. The frontend owns the full authorize→callback round-trip (per `oauth.service.ts`'s existing docblock: the backend is a single POST callback, not a redirect-issuing endpoint) — new `lib/oauth.ts` builds each provider's authorize URL directly from `NEXT_PUBLIC_GITHUB_CLIENT_ID`/`NEXT_PUBLIC_GOOGLE_CLIENT_ID` (client IDs aren't secret) and does CSRF-mitigating `state` round-tripping via `sessionStorage`. - **Pipelines: push to account + conflict prompt.** `PipelineBuilder` gets a "Save to account"/"Push update to account" button (signed-in only) via new `lib/pipeline-sync.ts`. Before overwriting an already-synced pipeline, it re-fetches the server copy's `updatedAt` and compares against what was recorded at the last successful sync; a mismatch throws `PipelineConflictError`, which the UI surfaces as a confirm dialog ("the account version has changed — overwrite it?") before retrying with `force: true`. This is the "user-visible conflict prompt for pipelines" DATABASE.md §7 calls for — last-write-wins once confirmed, not a real three-way merge. `PipelineRecord` (Dexie) gained optional `syncedId`/`syncedUpdatedAt` fields; no Dexie version bump needed since they're unindexed.
