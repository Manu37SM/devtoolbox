# AUDIT_REPORT.md

Planning-phase audit for DevToolbox. Records the key decisions made during architecture/planning, the reasoning behind them, known risks, and items intentionally left open for the implementation phase. Treat this as the paper trail for "why does the system look like this" — update it at the end of each major phase, don't just add to FEATURE.md/ARCHITECTURE.md silently.

## 1. Scope of This Audit

Covers the planning phase only: research, blueprint (ARCHITECTURE.md), feature catalog (FEATURE.md), schema (DATABASE.md), API design (API.md), design system (UI_GUIDELINES.md), dev process (DEVELOPMENT_GUIDE.md), and repo scaffolding. No feature code has been implemented; `frontend/` and `backend/` contain folder scaffolding only.

## 2. Key Decisions & Rationale

| Decision | Rationale | Alternative considered |
| --- | --- | --- |
| Client-side-first execution for all deterministic tools | Matches category baseline (every credible competitor is client-side now, per research), removes infra cost/scaling concern for the bulk of the product, builds trust for sensitive payloads (API keys, tokens) | Server-side processing — rejected: adds cost, latency, and trust friction with no offsetting benefit for pure transforms |
| Next.js (App Router) over a pure SPA (Vite+React) | SEO requires real, statically generated, crawlable pages per tool (ARCHITECTURE.md §13) — a pure client SPA can't deliver that without significant extra tooling that Next.js provides natively | Vite SPA + prerendering plugin — rejected: reinvents what Next.js SSG already solves well |
| NestJS over a lighter framework (Express/Fastify raw) | Backend has genuinely separable domains (auth, sync, share, AI gateway, analytics) that benefit from NestJS's module/DI structure as the surface grows toward Phase 4 (teams, admin, public API) | Express + manual structure — rejected: would likely converge on reinventing Nest's patterns by Phase 3 anyway |
| PostgreSQL + Prisma | Relational shape (users, ownership, join tables for orgs) is a natural fit; Prisma's typed client keeps the shared-types story clean with `packages/shared` | MongoDB — rejected: no document-shaped data that benefits from schema flexibility here; relational integrity (ownership, cascades) matters more |
| REST over GraphQL | Resource shapes are simple CRUD plus a small task-specific AI surface; GraphQL's benefits (flexible nested queries) don't apply to this data shape | GraphQL — rejected for now; revisit only if Phase 4 team/admin dashboards develop genuinely complex nested query needs |
| AI Gateway as task-specific endpoints, not a generic chat passthrough | Keeps prompts server-controlled and reviewable, avoids prompt-injection risk of exposing a raw model passthrough, keeps request/response shapes typed | Generic `/ai/chat` endpoint — rejected: harder to rate-limit/cost-control per feature, harder to keep safe against payload-embedded instructions |
| Tool content never used in product analytics | Non-negotiable per ARCHITECTURE.md privacy NFR; also removes an entire category of security/compliance risk | N/A — not seriously considered otherwise |
| Local-first data model (IndexedDB) with optional server sync | Lets the entire MVP ship with zero required backend for the core experience, matches "no signup required" goal, and keeps the free tier meaningfully free | Server-required accounts — rejected: contradicts the no-login-required product goal and adds infra cost from day one |
| Monorepo (npm/pnpm workspaces + Turborepo) | Shared types (`packages/shared`) between frontend/backend need one source of truth; a monorepo keeps DTO drift from happening | Separate repos — rejected: DTO/type drift risk outweighs the marginal deployment-independence benefit at this team size |

## 3. Competitive Research Summary (see ARCHITECTURE.md §4 for full detail)

Reviewed: single-tool SEO sites (jsonformatter.org, json.site), aggregator web suites (AdminSo DevToolbox, Converter360, developer-toolbox.dev, fmt.hjlabs.in), and native/offline apps (DevToys, DevUtils.app, DevTools-X). Findings that directly shaped this blueprint:

- Client-side execution and "no signup" are now baseline expectations, not differentiators — confirmed the architecture's hard default rather than treating it as a headline feature.
- "Smart detection" (native apps auto-selecting a tool from clipboard content) has no strong web equivalent — informed the command palette's smart-paste requirement (FEATURE.md, cross-cutting features).
- No competitor treats tool chaining/workflows as first-class — informed the Pipelines feature as a Phase 2 differentiator.
- No competitor has a real AI layer beyond a single bolted-on "AI code gen" tool — informed the AI Gateway architecture and Module 10 tool set.
- Aggregator sites are visually near-identical to each other — informed the emphasis on a distinctive design system (UI_GUIDELINES.md) as a differentiator in its own right.

## 4. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| AI Gateway cost overrun from abuse (scripted usage against free tier) | Medium | Medium | Per-IP + per-user rate limits (API.md §12), response caching for idempotent requests, tiered model routing (Haiku for cheap tasks) |
| SEO underperformance vs. established single-tool domains with years of backlinks | Medium | High (core acquisition channel) | Breadth + internal linking strategy, genuinely useful content per tool page (not thin filler), long-tail coverage across 60+ tools compounds over time — accept this is a multi-quarter effort, not instant |
| "Breadth over depth" perception — a competitor could out-feature us on any single tool | Low-Medium | Medium | Prioritization (FEATURE.md) intentionally matches or exceeds competitor depth on the highest-traffic tools first; coherence/workflow value compounds where competitors can't easily follow |
| Scope creep — 60+ tools is a lot of surface to maintain at quality | High | Medium | Strict tool contract (DEVELOPMENT_GUIDE.md §5) keeps marginal cost per tool low and consistent; phased roadmap prevents building everything before validating the MVP core |
| Prompt injection via tool payloads reaching the AI gateway (e.g., a "diff summary" input containing instructions aimed at the model) | Medium | Medium-High | AI gateway system prompts explicitly frame user content as data, not instructions (CLAUDE.md rule 7); output is always constrained to the task shape (e.g., diff-summary can't emit arbitrary free-form actions) |
| Local-first data model complicates sync conflict resolution once accounts ship | Medium | Low-Medium | Last-write-wins with user-visible conflict prompt for pipelines specifically (the one entity worth protecting from silent overwrite) — documented in DATABASE.md §7, to be implemented in Phase 3 |
| Free-forever core conflicts with sustainable unit economics at scale | Low-Medium | High (long-term) | Client-side execution keeps marginal cost per tool-use near zero; the costed surfaces (AI, network proxies, storage) are exactly where Pro-tier quotas apply (ARCHITECTURE.md §14) |

## 5. Open Items for Implementation Phase

These are intentionally deferred — not oversights, but decisions better made with real usage data or during hands-on implementation:

- Exact model routing table per AI tool (which tasks get Haiku vs. Sonnet) — start conservative (cheapest model that meets quality bar), tune after real usage/cost data.
- Final choice of hosted vs. self-hosted product analytics provider (Plausible vs. PostHog vs. self-hosted) — either satisfies the privacy requirement; pick based on Phase 1 team bandwidth for self-hosting.
- Exact Pro-tier pricing — deferred to Phase 3 when there's usage data to model unit economics against.
- Object storage provider (S3 vs. R2 vs. Backblaze) — functionally interchangeable behind the abstraction in ARCHITECTURE.md §8.3; pick on cost at implementation time.
- Whether the plugin/marketplace system (ARCHITECTURE.md §15) uses WASM sandboxing or a server-review-only model for community tools — needs a dedicated security design pass before Phase 4, not decided here.
- Internationalization: framework is i18n-ready (NFR, §7) but no locales beyond English are scoped for translation work yet — revisit after MVP traction data shows demand.

### 7.3 Known gaps / tech debt for next session

- **Full monorepo `npm install` could not be completed in this working session** — the sandboxed shell environment enforces a ~44s hard timeout per command with no process/state persistence across separate command invocations (each is its own isolated namespace; background `nohup`'d processes are killed when the invocation ends, they do not survive into the next tool call). **Root cause, refined in a later pass:** it is not (only) mounted-filesystem write speed as first suspected — a direct `npm install --loglevel=http` run against the real repo shows genuine, steady progress through package *resolution* (metadata fetches against the registry, hundreds of `cache stale`/`cache hit` lines per attempt) well within the 44s window, but **the repo has no `package-lock.json`**, so every fresh `npm install` invocation re-resolves the entire dependency graph from scratch rather than resuming from a prior attempt's partial resolution. Retrying the same command repeatedly therefore does *not* accumulate progress toward finishing a full install the way it does for small, targeted scratch-project installs (10–20 packages, which reliably complete in 1–2 retries even in `/tmp`) — each retry just resolves a similarly-sized but different slice of the graph and gets killed again before `node_modules` is ever written. The npm *download* cache (`~/.npm`, confirmed >800MB after this session's scratch-project work) is warm and not the bottleneck; dependency-graph *resolution* time for this dependency set (Next.js + Storybook + its addons + Playwright + ESLint + Radix + CodeMirror, all at once, no lockfile) is. **Practical implication:** this can't be worked around from within this sandbox's command-time constraint — there is no way to get a lockfile written or a `node_modules` tree materialized without a single `npm install` invocation that runs uninterrupted for as long as it needs (likely a few minutes for the first run on a cold-resolution repo; subsequent runs would be fast once a lockfile exists, since npm resumes from it). **Action item unchanged, with more specific reasoning:** run `npm install` once from a normal terminal (no time limit) to generate `package-lock.json`, commit it, then `npm run build`/`npm run typecheck`/`npm run storybook`/`npx playwright test` locally or in CI — all of this session's `.tsx`/`.ts` verification was done via isolated scratch-project typechecks and esbuild parse checks (see §7.5–§7.8) precisely because this full-repo install path isn't achievable here; it has not been compiled or run end-to-end by any tool in this session.
- **Git history exists but this sandbox can't commit to it.** Corrected from an earlier, inaccurate note in this file: the repo *does* have history (`git log` shows 2 prior commits, `origin` is set to a real GitHub remote) and `git status`/`git log`/`git diff` all work fine from this sandbox. What doesn't work is writing: `git add`/`git commit` fail with `Unable to create '.git/index.lock': File exists`, and a stale `.git/index.lock` file can't even be deleted (`rm -f` on it returns `Operation not permitted` despite the sandbox user owning the file with `rwx` permissions) — this is a Windows-mount-layer quirk, not a real lock held by another process. **Action item:** commit this session's changes from a normal terminal on the host machine (outside this sandbox), where the mount restriction doesn't apply; if `.git/index.lock` still exists there and blocks a commit, it's safe to delete manually (confirmed no other git process is actually running).
- **All 29 P0 tools are now shipped** — the Phase 1 tool backlog per FEATURE.md's "20 P0 tools" MVP target is complete (in fact all 29 P0-priority rows across every module are done, slightly exceeding the original MVP scope). Remaining Phase 1 work is the cross-cutting platform features below, not more tools.
- **Pipelines, PWA/offline, smart-paste completion polish** — Phase 2 scope per FEATURE.md's roadmap, not started.

### 7.7 CodeMirror 6 integration (this pass)

Closed the CodeMirror gap flagged in §7.2/§7.3 (UI_GUIDELINES.md §4/DEVELOPMENT_GUIDE.md's `CodeEditor` component):

- **New dependencies, flagged and approved before adding** (per CLAUDE.md rule 10): `@codemirror/lang-json`, `-javascript`, `-css`, `-html`, `-xml`, `-yaml`, `-markdown`, `@codemirror/language`, `@codemirror/commands`. Documented in ARCHITECTURE.md §8.2.
- **`components/ui/CodeEditor.tsx`** — the real `CodeEditor`, replacing `Textarea` as the input for tools whose content is a real language. Deliberately mirrors `Textarea`'s exact `value`/`onChange` contract (`onChange` receives a synthesized `{ target: { value } }` shape, not CodeMirror's native string callback) specifically so it's a drop-in swap requiring only an import change and a `language` prop in each `ToolView.tsx` — no changes to `onChange` handlers, state shape, or transform logic anywhere. ### 7.10 First real `npm run build` — three genuine defects found and fixed

With `npm install` finally completing (§7.9), `npm run build` was run for the first time in this project's history. It surfaced three real, previously-undetectable-in-sandbox issues:

**Fix 1 — `backend/tsconfig.json` regressions, self-inflicted.** An earlier fix (this session, responding to an editor deprecation warning — see the earlier, now-superseded note in this file) set `moduleResolution: "Node16"` while leaving `module: "CommonJS"`, an invalid pairing TypeScript hard-errors on (`TS5110`). The same fix set `rootDir: "./src"`, which conflicts with `backend/tsconfig.json`'s own `paths` entry pointing at `@devtoolbox/shared` under `../packages/shared/src` — outside that rootDir (`TS6059`). **Fix:** `module` changed to `"Node16"` to match `moduleResolution` (both must agree), and `rootDir` changed to `".."` (the actual common ancestor of `backend/src` and `packages/shared/src`, which is what the original editor warning had suggested in the first place). This shifts build output one level deeper (`dist/backend/src/main.js` instead of `dist/main.js`); `backend/package.json`'s `start` script updated to match.

**Fix 2 — three backend dependencies used in code but never added to `package.json`:** `helmet` and `@nestjs/config` (both imported in `main.ts`/`config.module.ts`) and `@types/express` (needed for `Response` typing in `common/filters/global-exception.filter.ts`). This gap predates this session — likely present since the original scaffold — and only surfaced now because this is the first time `tsc`/`nest build` actually ran against this code. Added all three.

**Fix 3 — `html-minifier-terser` (added in §7.5 for the HTML Beautifier's Minify mode) broke the frontend production build.** Its `clean-css` dependency unconditionally `require`s Node core modules (`fs`, `path`, `os`) in a source-map-reading code path that our usage never actually invokes (we only call `minify()` on an in-memory string) — but webpack still tries to resolve those modules for the client bundle and fails, since they don't exist in a browser. This is a known category of issue for Node-oriented libraries used client-side, not something the earlier scratch-project `tsc --strict` verification in §7.5 could have caught (that check only validates types, not whether webpack can actually bundle the code for a browser target — a real gap in this session's verification methodology, worth remembering for any future client-side dependency addition). **Fix:** standard Next.js workaround — `frontend/next.config.mjs` now sets `config.resolve.fallback = { fs: false, path: false, os: false }` for client (non-server) builds, telling webpack to treat those modules as unavailable rather than erroring. Safe here because the only code paths that reference them are never actually executed by our usage.

**Fix 4 — also fixed, unrelated to the build failure itself:** `next build` warned about an ambiguous workspace root, having found and preferred an unrelated `package-lock.json` sitting in the user's home directory over the actual project root. `frontend/next.config.mjs` now sets `outputFileTracingRoot` explicitly to the monorepo root so this can't happen regardless of what other lockfiles exist elsewhere on the machine.

**Fix 5 — `app/tools/[slug]/page.tsx` used the pre-Next-15 synchronous `params` convention.** Confirmed via the user's second build attempt, after fix #3 let webpack finish compiling and the build reached Next's own generated route-type checker (`.next/types/app/tools/[slug]/page.ts`): `Type 'ToolPageProps' does not satisfy the constraint 'PageProps' — params is missing Promise properties`. Next.js 15 made dynamic route `params` (and `searchParams`) async — a documented breaking change from Next 14 — and this page was written against the old synchronous shape (`params: { slug: string }` instead of `params: Promise<{ slug: string }>`), in both the page component and `generateMetadata`. This is the only dynamic route in the app (confirmed via a repo-wide grep for `params:`/`searchParams:` under `app/`), so no other route needed the same fix. **Fix:** `ToolPageProps.params` retyped as `Promise<{ slug: string }>`; `ToolPage` and `generateMetadata` both made `async` and now `await params` before use.

**Also observed — Next.js auto-modified `frontend/tsconfig.json`** during this build (`allowJs: true` added, `.next/types/**/*.ts` added to `include`) — this is standard, expected, one-time Next.js scaffolding behavior for any tsconfig missing those fields, not a regression. `strict: true` (inherited from `tsconfig.base.json` via `extends`) is untouched, since Next only fills in missing fields and never overrides ones already set through `extends`. No action needed.

**Fix 6 — `frontend/tsconfig.json`'s `include` (`**/*.ts`, `**/*.tsx`) swept up Storybook stories and Playwright specs into `next build`'s own type-check pass**, which they were never meant to be part of. Confirmed via the third build attempt (after fix #5 cleared the `params` error): `next build`'s type-checker failed on `DualPane.stories.tsx` — `StoryObj<typeof DualPane>` requires an `args` property even when using a custom `render` function, since `DualPane`'s `input`/`output` props have no defaults; a Storybook-authoring-time type contract with nothing to do with the actual app. Rather than reshaping the story to satisfy a constraint it doesn't need to satisfy for its own purpose (Storybook's own dev/build tooling handles `.stories.tsx` files through a different, more permissive path than a strict project-wide `tsc` pass), the correct fix is scoping: `frontend/tsconfig.json`'s `exclude` now lists `**/*.stories.tsx`, `.storybook`, `e2e`, and `playwright.config.ts`, so neither `next build`'s type-check nor `npm run typecheck` (which uses the same tsconfig) touch them. This also means `.stories.tsx`/`e2e/*.spec.ts` type correctness is no longer verified by `npm run typecheck` going forward — Storybook and Playwright each have their own separate type-checking path when actually run (`npm run storybook`, `npm run test:e2e`), which is the appropriate place for that, not the app's own build.

**Fix 7 — `random-generator/ToolView.tsx` had a real, pre-existing type bug**, confirmed via the fourth build attempt (after fix #6 cleared the Storybook type-check leak): `stringOpts`'s `useState({ ..., charset: "alphanumeric" as const })` had no explicit type annotation, so TypeScript inferred `charset` as the narrow literal type `"alphanumeric"` from the initial value rather than the full `"alphanumeric" | "alpha" | "numeric" | "hex"` union the `<select>`'s `onChange` handler needs to assign. Every other tool's `useState` calls with a similar shape already use an explicit type argument (`useState<XxxOptions>({...})`) — confirmed via a repo-wide grep for `useState({` across every `ToolView.tsx`, which returned only this one case — so this bug was isolated to this one tool, not a systemic pattern needing a broader sweep. **Fix:** annotated `stringOpts`' `useState` with `Omit<Extract<RandomGeneratorOptions, { kind: "string" }>, "kind">`, reusing the schema-derived union instead of hand-duplicating it.

`npm run build` succeeds end-to-end for both workspaces, confirmed via the user's local run — `turbo`'s summary reports "2 successful, 2 total." `backend` compiles via `nest build` with zero errors; `frontend` compiles, typechecks, and statically generates all 33 pages (29 tool pages + home + `/_not-found` + 2 more) via `next build`, with no errors of any kind. `npm run typecheck` also passes cleanly for both workspaces.

**Fix 8 — `npm run test` (frontend) failed on 2 of 33 test files** — not real test failures: Vitest had no `vitest.config.ts`, so it fell back to its default file-discovery glob (`**/*.{test,spec}.*`), which matched both our own unit tests (always named `*.test.ts` per DEVELOPMENT_GUIDE.md §5's tool contract) and the Playwright specs under `e2e/` (named `*.spec.ts`, per Playwright's own convention). Vitest tried to execute the Playwright specs, which use Playwright's own `test()` API and errored immediately ("Playwright Test did not expect test() to be called here"). Same category of scoping leak as fix #6 (Storybook stories into `next build`'s type-check), just for Vitest instead of `tsc`. **Fix:** added `frontend/vitest.config.ts` with an explicit `test.include: ["src/**/*.test.{ts,tsx}"]` and `test.exclude` listing `e2e/**` and `.storybook/**`, so Vitest only ever discovers the tool `transform.test.ts` files and `lib/*.test.ts` files it's meant to.

**Final status: the full test suite passes.** Once fix #8 landed, `npm run test` for `frontend` reports **31 test files, 247 tests, all passing** — every `transform.ts` across all 29 tools plus `lib/fuzzy-search.ts`/`lib/smart-detect.ts`, run for the first time against the real installed packages rather than this session's isolated scratch-project checks. `backend`'s `test` script now uses `jest --passWithNoTests` and exits cleanly, honestly reflecting that backend currently has zero test files (25 scaffolded module/controller/service files across `auth`/`sync`/`share`/`users`/`admin`/`analytics`/`ai-gateway`, none covered by tests) — expected given FEATURE.md's phased roadmap scopes backend accounts/sync/sharing to Phase 2/3, not a regression from this session. `npm audit --omit=dev` remains at the 2 accepted-risk Next-bundled findings (postcss/sharp) from earlier in this section; nothing new surfaced across build, typecheck, or test. **This is the first time this entire project has gone through a complete, real, green build → typecheck → test cycle.** Remaining work: `npm run storybook`/`npm run test:e2e` still haven't been run against a live app (only typechecked/parsed — see §7.7/§7.8), and committing this session's work is still blocked by the `.git/index.lock` issue (§7.3) inside this sandbox specifically — needs a normal terminal.

### 8.2 Working method — parallel subagents, not solo sequential implementation

Unlike §7 (built by a single session working through tools roughly one at a time), most of Phase 2's tool volume was built by dispatching multiple general-purpose subagents in parallel, each given a self-contained brief covering a batch of 4-7 tools with the exact contract (schema/transform/tests/ToolView/index/content.mdx), explicit file-scope boundaries (never touch `registry.ts`/`tool-view-registry.ts`/`package.json` — those get wired up by hand afterward to avoid concurrent-edit conflicts on shared files), and enough repo context (existing reference tools to model, shared component APIs) to work without seeing the rest of the conversation. ### 8.3 Real defects found and fixed this phase (via the user's local build/test cycle, same pattern as §7.10)

Each of these was caught by an actual `npm run typecheck`/`npm run test` run on the user's machine, not by sandbox scratch-project verification — reinforcing §7.9's closing point that a real full-tree build is the only check that reliably catches cross-file/dependency-level defects:

1. **`csv-tsv`'s `escapeCell` over-quoted TSV output** — quoted a cell whenever it contained a delimiter, a bare `"`, *or* a newline, but TSV has no quoting convention; fixed to only quote on the actual target delimiter.
2. **`sql-formatter`'s "multi-statement" test asserted an exact-substring layout** (`"SELECT 1"` on one line) that didn't match `sql-formatter`'s real (correct) multi-line output — a bad test assertion, not a real transform bug.
3. **`gzip-deflate`'s error fallback message never fired** when the caught `Error`/`DOMException` had an empty `.message` (happens on some runtimes for a bad gzip header) — fixed to fall back whenever the caught message is empty, not just when it's not an `Error` instance.
4. **Multiple `noUncheckedIndexedAccess` strict-mode gaps** in the pipelines feature (`PipelineBuilder.tsx`'s array-swap reorder logic, `db.ts`'s `createPipeline` return type, both pipeline test files' array-index assertions) — all `Record`/array indexing under this tsconfig flag returns `T | undefined`, and several of these were written assuming plain `T`. Fixed with explicit non-null assertions at points where the surrounding logic (an array-length guard, a `toHaveLength` assertion, an auto-increment PK) already guarantees presence.
5. **`smart-detect.test.ts`'s hash-digest fixtures had typos** — the MD5/SHA-1 test strings were each missing one character (hand-typed from memory rather than computed), so the length-based hash detector legitimately failed to match a 31/39-character string. Fixed by computing the real digests and using those.
6. **`svg-optimizer`'s `removeViewBox` option silently no-op'd** — svgo v4's `preset-default` doesn't include `removeViewBox` at all, so passing it via `overrides` does nothing (svgo warns about this at runtime, which is also what pointed to the fix). Fixed by adding `"removeViewBox"` as its own separate plugin array entry when requested, exactly as svgo's own warning suggests.
7. **`favicon-generator`'s zip bundling failed in the test/Node environment** — `jszip` only accepts/produces `Blob` when it detects full browser Blob/FileReader support, which is false under this repo's Node-based Vitest run even though `Blob` itself is a real global there. Fixed by routing both directions through `ArrayBuffer` instead (`blob.arrayBuffer()` in, `new Blob([arrayBuffer])` out) — works identically in real browsers, not just a test-environment workaround.

### 9.2 Deliberate deviations from the docs (CLAUDE.md rule 10)

1. **`VerificationToken` table added, not in DATABASE.md's original ERD.** Needed to actually implement the email-verify/password-reset routes API.md already specified. Single table discriminated by `type` rather than two near-identical tables. Documented in DATABASE.md directly (new "Implementation notes" subsection under §3) and CHANGELOG.md.
2. **UUIDv4 primary keys, not UUIDv7 as DATABASE.md's design principles specify.** Prisma/Postgres don't generate UUIDv7 natively; a real fix means either an app-side UUIDv7 library on every create call or a Postgres extension, neither of which felt justified to add mid-feature without asking. Tracked as follow-up debt, not a blocker — UUIDv7 was specified for index locality (a performance concern), not correctness.
3. **History encryption uses one server-wide AES-256-GCM key, not a per-user derived key** as DATABASE.md's `HistoryEntry` comment describes. A true per-user scheme needs a KMS or key-wrapping design that's a project of its own; a single key with a random IV per record is the conventional interim default and still satisfies the actual security property (encrypted at rest, not plaintext in the DB).
4. **OAuth implemented as a manual two-fetch code exchange, not passport-github2/passport-google-oauth20.** Those libraries assume the backend owns the full redirect round-trip (an "authorize" route plus a "callback" route, both behind an `AuthGuard`); API.md's actual contract is a single `POST /auth/oauth/:provider/callback` with a `code` the frontend already has. Bending passport to fit that shape was more complexity than just calling GitHub's/Google's token and userinfo endpoints directly. The two passport OAuth packages (already present in `backend/package.json` from earlier scaffolding) were removed as unused; `passport-jwt` stays, since the access-token strategy does fit passport's normal model.
5. **No transactional-email provider.** ARCHITECTURE.md's stack doesn't name one yet. `EmailService` logs verify/reset links to the server console — functionally complete for local dev/testing, not production-ready. Flagged as a pre-production blocker, not silently shipped as if it were done.
6. **`@tanstack/react-query` was not reinstalled** despite ARCHITECTURE.md §8.2 naming it for "any server state (auth session, synced data, AI responses)." None of the new pages needed its caching/background-refetch/invalidation machinery — plain `fetch` + `useState` (the same pattern Module 8's tools already established) covered every case here. If a future AI Gateway wave needs streaming/optimistic-update ergonomics that plain fetch makes painful, that's the point to actually add it back — not before.
7. **CORS bug fixed in passing, not introduced by this wave:** `main.ts` was calling `enableCors({ origin: process.env.NEXT_PUBLIC_API_BASE_URL ? true : false, credentials: true })` — `origin: true` reflects any request's origin back, which combined with `credentials: true` is a known anti-pattern that effectively disables CORS's protection for cookie-authenticated requests. Since this wave is the first thing that actually puts a real credentialed cookie (the refresh token) in play, leaving it as-is wasn't an option — fixed to pin against the new `FRONTEND_URL` env var.

Populates `req.user = { userId, email }` in the exact shape `JwtAccessStrategy` does, so `PlanThrottleGuard` composes after it identically to every session-authed rate-limited route — no new rate-limit machinery, just a new way to arrive at `req.user`. Throws `UnauthorizedException` (401) for a missing/invalid/revoked key, `ForbiddenException` (403) for a valid key on a non-PRO/TEAM account, matching the distinction API.md §12 documents.
- **`PublicApiModule`** (API.md §12): `POST /v1/public/hash` (md5/sha1/sha256/sha512) and `/v1/public/json-validate` — exactly ARCHITECTURE.md §14.3's own two examples, not an attempt at broader coverage. Both are pure `node:crypto`/`JSON.parse` operations reimplemented directly in the backend rather than importing frontend tool code — the frontend's `transform.ts` files are pure by contract (CLAUDE.md rule 3) but live under Next.js-specific path aliases/tooling not meant to be pulled into a NestJS build; two ~5-line functions were cheaper and cleaner than building a shared-import bridge for two tools.
- **`@devtoolbox/cli`** (new `packages/cli` workspace): `devtoolbox hash <algorithm> <input>` and `devtoolbox json-validate <file|->` (exit code reflects validity, so it's usable as a CI gate directly). Reads `DEVTOOLBOX_API_KEY`/`DEVTOOLBOX_API_URL` from the environment, never a CLI flag (flags leak into shell history/process lists). Deliberately zero new dependencies: Node 22 LTS's built-in `fetch` (already this repo's documented Node baseline, DEVELOPMENT_GUIDE.md) instead of an HTTP client library, manual `argv` parsing instead of `commander`/`yargs`, `node:test`/`node:assert` instead of adding a test framework to a package this small.
- **Frontend:** new "API keys" section on `/account`, gated on `user.plan !== "FREE"` (shows an upsell sentence otherwise), following the same list/create/revoke UI pattern already established for OAuth account-linking on the same page.

### 14.2 Deliberate deviations / notes (CLAUDE.md rule 10)

- **Public API surface is intentionally two tools, not a mirror of the catalog.** ARCHITECTURE.md §14.3 explicitly scopes this to "select tools... for CI pipelines" with hash generation and batch JSON validation as its own examples — building more than that without a specific requested tool would be scope invention, not scope delivery.
- **Rate limit is per-user, not per-key**, despite multiple keys per account being a real use case (one per CI pipeline/environment) — reuses `PlanThrottleGuard`'s existing per-user identity resolution rather than adding a new per-key dimension to that guard. If usage data later shows this is too coarse (one noisy pipeline starving another), revisit; not assumed a problem yet.
- **No billing enforcement beyond a plan-field check** (at the time this section was written — **resolved in §15**, the very next pass, once the user asked for billing next). `validateKey` checks `user.plan` is PRO/TEAM; until §15 shipped, the only way to satisfy that was an admin manually setting a user's plan (`POST /admin/users/:id/plan`, already existed). Left this note in place rather than rewriting history — it's what was true and honestly flagged at the time.

Everything else (backend `tsc --noEmit` outside this one file, `packages/cli`'s `tsc --noEmit`, all new unit tests via mocked Prisma) was verified.

Same class of sandbox-only limitation as the Rollup/`vitest` issue noted earlier this session — `tsc --noEmit` passed cleanly for the whole package, and the test logic was reviewed by hand, but the user should run `npm run test --workspace @devtoolbox/cli` locally to get a real pass/fail signal.

**Current overall status (end of §14):** Public API/CLI groundwork shipped for 2 of an eventual larger tool set; 3 of 4 Phase 4 items (team workspaces, browser extension, plugin marketplace) remain fully unscoped. Two verification gaps are open pending the user's local environment: Prisma client regeneration (`npm run db:migrate:dev`) and `packages/cli`'s test run (`npm run test --workspace @devtoolbox/cli`) — both blocked by sandbox-only network/platform limitations, not known code defects.

## 15. Pro tier / billing (Stripe)

Directly motivated by §14.2's own flagged gap: the Public API's PRO/TEAM check existed but had no real way to be satisfied short of an admin manually editing a row. Scope: Stripe Checkout + Customer Portal (both Stripe-hosted, no custom payment UI), a `Subscription` table for support/debug visibility, and syncing `User.plan` from webhooks — not a general subscription-management framework, and not usage-based/metered billing (the existing `PlanThrottleGuard`/AI Gateway quota system already handles usage limits per plan tier; this section only handles how a user gets into a tier).

### 15.1 What shipped

- **`BillingService`/`BillingController`** (`backend/src/modules/billing/`): `POST /billing/checkout-session` (creates a Stripe customer on first use, returns a Checkout redirect URL), `POST /billing/portal-session` (Customer Portal redirect for managing/canceling), `GET /billing/subscription` (current status for the account page), `POST /billing/webhook` (Stripe-signature-verified). Same lazy-client/undefined-vs-null-resolved pattern as `AiGatewayService.getClient()` — a missing `STRIPE_SECRET_KEY` produces a clear `ServiceUnavailableException` (503) from any route that actually needs Stripe, not a boot failure.
- **`Subscription` model + `User.stripeCustomerId`** (migration `20260811130000_add_billing`, DATABASE.md §3): `SubscriptionStatus` mirrors Stripe's own status strings 1:1 rather than inventing a coarser enum, so the webhook handler passes `subscription.status.toUpperCase()` straight through with no translation table to keep in sync with Stripe's own semantics.
- **First webhook-signature-verification pattern in this codebase.** Every other inbound-request surface either requires session/API-key auth or (Module 8's webhook-inbox tool) doesn't authenticate the sender at all because it's *meant* to capture arbitrary requests for debugging. `main.ts` now boots with `{ rawBody: true }` (Nest's built-in option) so `req.rawBody` is available on every route without affecting normal JSON body parsing elsewhere — `stripe.webhooks.constructEvent` needs the exact bytes Stripe signed, not a re-serialized copy of the parsed body.
- **Plan sync logic fails closed, not open.** `syncSubscriptionFromStripe` only grants the paid plan for `ACTIVE`/`TRIALING` status; `PAST_DUE`, `CANCELED`, `UNPAID`, etc. all downgrade to `FREE` immediately rather than waiting for a final cancellation event. A billing hiccup degrades to the free (fully-functional) tier, never leaves a lapsed subscriber on a paid tier they're not paying for — consistent with ARCHITECTURE.md §14's "no core tool ever paywalled" framing, applied to the *removal* side of a paid tier too.
- **Frontend:** new "Plan & billing" section on `/account` (upgrade buttons for FREE users; a "Manage billing" button + renewal/cancellation date for PRO/TEAM users, fetched from `GET /billing/subscription`).
- New env vars: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID_PRO`, `STRIPE_PRICE_ID_TEAM` — all optional, same "degrade with a clear error, don't fail boot" treatment as every other optional integration key in this codebase.

### 15.2 Deliberate deviations / notes (CLAUDE.md rule 10)

- **New top-level dependency (`stripe`).** Flagged before starting (research pass confirmed no payment provider was already approved anywhere in ARCHITECTURE.md) and confirmed by the user choosing "Pro tier / billing" after being told it meant Stripe integration specifically. Added to `backend/package.json` only — no frontend Stripe.js dependency, since Checkout/Portal are both server-initiated redirects, not embedded card forms.
- **Account deletion doesn't cancel the Stripe subscription yet.** DATABASE.md §4's retention table flags this explicitly — a deleted DevToolbox account can leave an orphaned active Stripe subscription still billing the (now-deleted) user. Tracked as a follow-up for whoever wires up the account-deletion hard-purge job; not silently ignored, but genuinely not implemented in this pass.
- **Rate limits for `/billing/checkout-session`/`/billing/portal-session`** (10/hour/user, API.md §15) are a judgment call, not a specified number anywhere — picked to comfortably cover legitimate retry/plan-switching behavior while still bounding abuse, same reasoning basis as every other rate limit table entry in this codebase (none of which cite an external source either).

The user should treat this pass as needing a real local `npm install && npm run typecheck && npm run test && npm run db:migrate:dev` pass before considering it done, more so than any earlier section in this document.

## 16. Browser extension (Manifest V3)

Scope, chosen the same way as the Public API tier (§14): a curated subset of tools, not the whole catalog, and no dependency on `frontend`/`backend`/`packages/shared`. A browser extension's runtime environment — service workers, `chrome.scripting`, no DOM until injected — doesn't share enough with either app to make cross-importing worthwhile for a handful of small pure functions.

### 16.1 What shipped

- **`@devtoolbox/extension`** (`packages/extension/`): Manifest V3, `manifest_version: 3`, `background.service_worker` + `action.default_popup`, permissions `["contextMenus", "activeTab", "scripting"]`. Right-click a text selection on any page → "DevToolbox" submenu → Format JSON / Base64 Encode / Base64 Decode / URL Encode / URL Decode / Decode JWT (unverified).
- **`src/transforms.ts`**: six small pure functions (`TransformResult = { ok, output }`, never throws past its own boundary), reimplemented rather than imported from `frontend/src/modules/tools/*/transform.ts` — same rationale as the Public API's `hash`/`json-validate` endpoints (§14.1): those files are pure by contract (CLAUDE.md rule 3) but live behind Next.js path aliases/build tooling not meant to cross into this package's esbuild pipeline. `jwtDecode` explicitly decodes only, never verifies a signature (no key material available client-side) — both the function name and its output text (`// Header (unverified)` / `// Payload (unverified — signature not checked)`) say so, so the result can't be mistaken for a trust decision.
- **`src/background.ts`**: registers the context-menu tree on `chrome.runtime.onInstalled`, runs the matching transform against `info.selectionText` on click, then injects a self-contained overlay-rendering function into the active tab via `chrome.scripting.executeScript`. Deliberately no `content_scripts` entry in the manifest — nothing runs on any page until the user actually right-clicks and picks a tool, and the clipboard write happens from an explicit in-overlay "Copy to clipboard" button click (a guaranteed user gesture in the tab's own context), not from an async message hand-off that could lose transient-activation status.
- **`src/popup.ts`/`popup.html`**: toolbar-popup equivalent of the same six tools, for pasted (non-selected) text — a `<select>` of tools, a textarea, Run/Copy buttons. Runs entirely client-side in the popup's own DOM; no messaging needed since the transforms are pure.
- **Build**: `build.mjs`, a ~25-line `esbuild` script (`background.ts`/`popup.ts` → `dist/*.js`, `manifest.json`/`popup.html` copied alongside) — no bundler config file, since the package has exactly two entry points and no framework. `tsconfig.json` extends the repo's `tsconfig.base.json` with `allowImportingTsExtensions` (esbuild and the test runner both resolve explicit `.ts` import specifiers natively; only `tsc` needed the opt-in flag).
- **Tests**: `src/transforms.test.ts`, `node:test`/`node:assert` — same zero-new-test-framework choice already made for `packages/cli`. 8 cases: round-trip tests for Base64 (including non-ASCII) and URL encoding, valid/invalid JSON, a real (if fake-signed) JWT decode asserting the output is labeled unverified, and error-path assertions for each transform (never throws, always returns `{ ok: false, output: <message> }`).

### 16.2 Deliberate deviations / notes (CLAUDE.md rule 10)

- **New top-level dependencies (`esbuild`, `@types/chrome`, `tsx`, `typescript`)**, scoped to `packages/extension/devDependencies` only. `esbuild` was already present transitively via `vite`/`vitest` elsewhere in the monorepo, so this isn't a wholly novel toolchain choice, just the first place it's used directly. `tsx` mirrors its existing use for `packages/cli`'s dev loop.
- **No `content_scripts` entry**, even though the original design note in ARCHITECTURE.md §15 sketched a content-script + message-passing shape. Switched to on-demand `chrome.scripting.executeScript` injection during implementation because it (a) keeps the extension's footprint at zero on every page until invoked, and (b) sidesteps clipboard-permission ambiguity around writes triggered by cross-context messages rather than a direct in-page click. ARCHITECTURE.md §15 has not been re-edited to describe this narrower mechanism; noting it here per rule 10 rather than leaving the two documents silently disagreeing.
- **No icon assets.** `manifest.json` omits `icons`/`action.default_icon` — there are no PNG assets in this repo to point at, and generating placeholder brand icons wasn't in scope for this pass. Chrome loads and runs the extension fine without them (shows its generic default icon); this is a disclosed design-asset gap, not a functional one.
- **`popup.html`'s "Open full DevToolbox" link points at `https://devtoolbox.dev`**, a placeholder — this codebase has no canonical production domain defined anywhere yet. Update alongside whatever real domain gets chosen at deploy time.
- **Verified in this sandbox** (unlike §15's billing pass): `npx tsc --noEmit` clean, `node --test src/transforms.test.ts` (8/8 passing), and `node build.mjs` (produces a loadable unpacked `dist/` — `manifest.json`, `background.js`, `popup.js`, `popup.html`, sourcemaps). Not verified: an actual `chrome://extensions` "Load unpacked" smoke test, since this sandbox has no browser UI to drive one. The user should do a real load-unpacked pass before publishing.

**Current overall status (end of §16):** Browser extension MVP is code-complete and verified at the toolchain level (typecheck/test/build all pass). Remaining Phase 4 work: team workspaces, plugin marketplace (both unscoped); browser extension itself still needs a manual "Load unpacked" smoke test and, eventually, real icon assets and a Chrome Web Store listing before it can ship to users.

## 17. Team Workspaces (Phase 4, MVP scope)

Activates `Organization`/`OrganizationMember` — planning-phase scaffolding present in the schema since Phase 3 but never wired to any route. Scope deliberately narrower than ARCHITECTURE.md §14.2's original one-line description ("team workspaces with shared pipelines/snippets, SSO, priority support, custom branding for shared links"): this pass ships org CRUD, roles, shared snippets/pipelines, and an AI-usage dashboard; SSO, priority support (a process commitment, not code), and custom branding are not built. §17.2 covers why.

### 17.1 What shipped

- **`OrganizationsService`/`OrganizationsController`** (`backend/src/modules/organizations/`): `POST/GET/PATCH/DELETE /organizations`, `POST /organizations/:id/members` (add an existing user by email), `PATCH`/`DELETE /organizations/:id/members/:userId` (role change / remove), `GET /organizations/:id/usage` (API.md §17). - **`resolveEffectivePlan()`** (`backend/src/common/plan/effective-plan.ts`): the one piece of genuinely cross-cutting, security-relevant logic in this pass (CLAUDE.md rule 6). Wired into the two places ARCHITECTURE.md's monetization section actually promises a team benefit: `PlanThrottleGuard`'s rate-limit tier resolution, and `ApiKeysService.validateKey`'s PRO/TEAM gate for the Public API. Deliberately *not* used inside `/billing/*` itself — a user's own plan there is always their own, never inherited from an org. Only queries `organizationMember` when `ownPlan === "FREE"` (PRO/TEAM already get the top tier from their own plan, so the extra query is skipped).

- **No email-token invite/accept flow.** `POST /organizations/:id/members` adds an *existing* DevToolbox user immediately by email (404 if no account exists) — there's no pending-invite state, no email sent, no accept step. ## 18. Plugin Marketplace (Phase 4, v1)

The last unscoped Phase 4 item, and the only one this session flagged for explicit user confirmation before writing code (CLAUDE.md rule 10: it persists third-party executable content server-side by default, and introduces untrusted code execution — a genuinely new architectural pattern with no precedent anywhere else in this codebase). ARCHITECTURE.md §16 was written as a design-only pass first; the user then confirmed "build the plugin marketplace" before any implementation started.

### 18.1 What shipped

- **`Plugin`/`PluginVersion` models** (migration `20260811160000_add_plugin_marketplace`, DATABASE.md §3) + **`User.isAdmin`**. The latter is the first real implementation of the "admin" concept API.md §14's Admin routes already referenced by name — that module has been an empty stub with no actual gating since it was first scaffolded (§ earlier in this doc). A single boolean, not a role enum: there's exactly one privilege tier this pass needs to gate (the review queue), and a fuller role system would be speculative.
- **`PluginsService`** (`backend/src/modules/plugins/`): create (draft), submit version (validates + moves back to `IN_REVIEW` — every version re-enters review, not just the first), list published, get detail / get run payload (both with the same owner-or-public visibility shape as `SnippetsService.getOne`), admin review queue, approve/reject, suspend. Role/ownership checks live in the service layer, not just guards — same convention as `OrganizationsService` (§17.1).
- **Client-side execution, zero server-side WASM runtime.** `PluginRunner` (`frontend/src/components/plugins/`) loads a plugin's WASM inside an `<iframe srcDoc=... sandbox="allow-scripts">` — no `allow-same-origin`, so the frame gets a unique **opaque origin** automatically per the HTML spec, with no cookies, no localStorage, and no way to reach the parent's origin, all without deploying a dedicated subdomain (a simplification discovered during implementation — the original §16.1 sketch proposed a real second subdomain; `srcdoc` + `sandbox` alone achieves the same isolation property for free). The sandboxed document's own CSP (`connect-src 'none'; frame-src 'none'; img-src 'none'; style-src 'none'`) blocks all network egress as defense-in-depth on top of whatever the WASM import allowlist is supposed to prevent.
- **Hand-rolled minimal ABI**, documented in `PluginRunner.tsx`'s own comments: a plugin module must export `memory`, `alloc(len) -> ptr`, `transform(ptr, len) -> resultPtr` (result is a 4-byte little-endian length prefix followed by UTF-8 bytes). This is not wasm-bindgen or any standard binding generator — it's the smallest calling convention that lets a hand-written ~40-line JS harness marshal one string in and one string out without a code-generation dependency. `options` are accepted in the postMessage protocol but not yet marshaled into the WASM call (ARCHITECTURE.md §16.5's open question on the permission model applies here too).
- **3-second execution timeout**, enforced in the parent, not the sandbox (a hostile/hung plugin can't be trusted to enforce its own timeout). On timeout, the iframe's `srcdoc` is reassigned to force a fresh, uninitialized WASM instance for the next run — the same frame is never reused after a hang, exactly as §16.1.3 specified.
- **`devtoolbox plugin publish`** (`packages/cli`): new `PluginPublishClient` (`src/plugin-client.ts`), deliberately separate from the existing `DevToolboxClient`. See §18.2's rough-edge note for why it needed its own auth model.
- **Frontend:** `/plugins` (public listing), `/plugins/new` (create draft, session-authed), `/plugins/:slug` (detail — run UI for `PUBLISHED` plugins, a version-submission form for the owner), `/plugins/review-queue` (admin actions). Linked from the top nav (`AppShell.tsx`), alongside Pipelines/Snippets.
- **Tests:** 17 new cases in `plugins.service.spec.ts` (submission validation — size cap, magic number, ownership, suspended-plugin rejection; visibility rules for `getDetail`/`getRunPayload`; admin gating for the review queue/review/suspend; last-mile "accepts a valid submission" happy path). 3 new CLI argument-validation tests in `index.test.ts`, matching the existing style (only pre-network-call paths, consistent with how `hash`/`json-validate` are tested). All 17+3 pass in this sandbox; full backend/frontend `tsc --noEmit` also run (see §18.2 for the one known gap in that pass).

### 18.2 Deliberate deviations / notes (CLAUDE.md rule 10)

- **WASM stored as base64 text on `PluginVersion`, not S3-compatible object storage.** ARCHITECTURE.md §16.2's original sketch said "object storage, reusing `ShareLink.objectStorageKey`'s precedent" — investigating that precedent while implementing found it was aspirational, not real: `ShareLink.objectStorageKey` exists as a schema field and a DATABASE.md comment, but no S3/MinIO/`aws-sdk` client exists anywhere in `backend/src`, and `ShareService` never reads or writes that column. Building real object-storage infrastructure — a new top-level dependency, new env vars, a new failure mode — for a feature already hard-capped at 2MB decoded felt like the wrong place to spend this pass's budget. Postgres `TEXT` storage is genuinely fine at this size. If plugins ever need to exceed 2MB, object storage becomes the right call and should be built as its own pass (which would also finally make `ShareLink.objectStorageKey` real).
- **Static WASM inspection is size + magic-number only**, not the "reject any import outside an `abort`-only allowlist" parser §16.2 described. Parsing a WASM binary's import section correctly is a real parser, not a few lines — implementing a partial/buggy one would have been worse than being explicit that it doesn't exist yet. This is judged an acceptable gap *because* the sandbox itself (opaque-origin iframe, `sandbox="allow-scripts"` only, `connect-src 'none'` CSP) is the actual security boundary — a plugin's declared imports don't matter if the runtime environment can't act on network access, storage access, or the parent's origin regardless of what the module asks for. Static analysis was always meant to be defense-in-depth on top of that, never the only layer; a hostile WASM module rejected by static analysis today is worth catching, but its absence doesn't create a bypass of the actual containment.
- **Opaque-origin `srcdoc` iframe instead of a dedicated subdomain.** Same class of "simpler thing achieves the same property" discovery as §16.1's design predicted might happen during implementation (that section already flagged this as an open possibility, not a surprise) — no DNS/deployment configuration needed, and the isolation guarantee (`allow-scripts` without `allow-same-origin` → unique opaque origin per HTML spec) is equivalent for this threat model.
- **CLI plugin publishing uses `DEVTOOLBOX_ACCESS_TOKEN` (a session token), not `DEVTOOLBOX_API_KEY`.** The existing `ApiKeyAuthGuard`/`ApiKeysService.validateKey` pair enforces a PRO/TEAM plan gate (§13/§14.1) — appropriate for the Public API tier, wrong for plugin publishing, which is deliberately open to any signed-in user (consistent with "never paywall," ARCHITECTURE.md §14). Reusing the API-key guard would have silently paywalled community contribution. The real fix — a longer-lived, narrowly-scoped "publish token" type distinct from both session tokens and Public API keys — wasn't built speculatively; `DEVTOOLBOX_ACCESS_TOKEN`'s short expiry (needs manual refresh from the browser) is a disclosed rough edge for this pass, tracked as a follow-up in the CLI's own doc comments (`plugin-client.ts`).
- **`User.isAdmin` has no admin-granting UI or seed script.** The only way to become an admin in this pass is a direct database update — appropriate for a first cut of a privilege that's currently used for exactly one thing (the review queue), but should get a real provisioning story (even just a documented `psql` command, or a CLI flag on the seed script) before this goes further than a single trusted operator.
- **No object-storage-style malware/antivirus scanning of submitted WASM.** Static analysis (§18's size + magic-number check) and the runtime sandbox are the only two layers; there's no third-party scanning step in the human-review process either (§16.2's review step is a documented manual process, not automated tooling). Not a gap unique to this pass — no file-upload surface in this codebase has ever had AV scanning — but worth naming since this is the first surface where the uploaded content is *executable* rather than passive data.
- **Verification is clean except for the same class of stale-Prisma-client gap already disclosed in §17.2.** `plugins.service.ts` itself doesn't typecheck against the currently-generated Prisma client (`plugin`/`pluginVersion` properties, `isAdmin` field — all missing from the client generated before this pass's schema edit), for the identical reason as §17.2: no network access to `binaries.prisma.sh` in this sandbox to re-run `npx prisma generate`. All of this pass's *logic* is verified via the unit tests (which mock Prisma entirely and don't depend on generated types beyond `as never` casts), and the two implicit-`any` bugs that surfaced alongside the stale-client noise were real and have been fixed. **The user must run `npx prisma generate && npx prisma migrate dev` locally before `npm run typecheck` will pass clean** — same instruction as §17.2, now covering three modules' worth of schema changes made across this session without a working local Postgres/network connection in the sandbox.

**Current overall status (end of §18):** All four Phase 4 items from FEATURE.md's original roadmap are now shipped in some form: Pro tier/billing (§15, full), Public API/CLI (§14, groundwork), browser extension (§16 cross-reference — curated MVP), team workspaces (§17, MVP), and plugin marketplace (§18, v1). Every pass in this session that touched `schema.prisma` (§15 billing, §17 team workspaces, §18 plugins) shares one real, disclosed, and consistent gap: this sandbox cannot reach `binaries.prisma.sh` to regenerate the Prisma client, so `npx prisma generate && npx prisma migrate dev` is a required step before any of Phase 4's newer code will typecheck or run against a real database. Everything else — Zod schemas, service logic, unit tests (mocked Prisma), frontend TypeScript, the extension's esbuild bundle — has been verified directly in this sandbox. (The user has since confirmed this step was completed locally — `npx prisma generate && npx prisma migrate dev` ran successfully, and `npm run typecheck`/`npm run test`/`npm run build` all pass on their machine.)

## 19. Audit-hardening pass (post-Phase-4)

With every Phase 4 item shipped, this session's user asked for a full audit-hardening pass over what had just been built, rather than starting new feature work — a cross-cutting security/accessibility/test-coverage review, per the same instinct that shaped every other section of this document (verify before moving on, disclose what's found). `/security-review` (the repo's own slash-command skill) couldn't run in this environment — it requires an actual git working directory, and this session's tools operate against a separate scratchpad — so the review was done via a scoped sub-agent read of every file touched by §17 (team workspaces) and §18 (plugins), plus the `PluginRunner` sandbox specifically, followed by manual fixes here.

### 19.1 Findings and fixes

- **[Fixed, high — upgraded from the review's own "medium" framing] `@PlanThrottle` applied at the class level on `OrganizationsController` and `PluginsController` silently never took effect.** `PlanThrottleGuard.canActivate` reads its config via `this.reflector.get(PLAN_THROTTLE_KEY, context.getHandler())` — handler-level only, no class-level fallback. Both controllers were built with `@PlanThrottle(...)` placed above `@Controller(...)` (a pattern that looks reasonable and matches how `@UseGuards` composes at the class level elsewhere in Nest, but doesn't work for this specific home-grown decorator). The practical effect: every route on both controllers had **no** per-plan rate limiting at all — only the app-wide flat `ThrottlerModule` baseline (300/min, `app.module.ts`) applied, not the differentiated anon/free/pro limits API.md §17/§18 document. Every other controller in this codebase (`api-keys`, `ai-gateway`, `public-api`, `billing`, `share`, `net`) already used the correct per-method pattern — confirmed by grep across `backend/src` before writing the fix, so this was isolated to the two newest controllers, not a systemic issue. **Fix:** moved `@PlanThrottle` onto every individual route handler in both controllers. `OrganizationsController`'s methods all share one `ORG_THROTTLE` config object with the same `route: "organizations"` string, preserving the originally-intended single shared 60/hour budget across the whole controller (rather than accidentally giving each route its own independent budget, which a naive per-method conversion would have done). `PluginsController`'s methods each get a distinct route name and a limit sized to what that route actually does — most stay near the original 120/hour, but `submitVersion` (the one route that can move up to 2MB per call) drops to 10/hour, directly addressing the review's separate storage-exhaustion finding below in the same fix.
- **[Fixed, medium] Storage-exhaustion risk on plugin version submission.** Before the throttle fix above, the shared 120/hour limit (which, per the bug above, wasn't even being enforced) would have allowed up to ~240MB/hour of stored WASM per user even if the metadata bug hadn't existed. `POST /plugins/:id/versions` now has its own 10/hour limit (`plugins.controller.ts`), bounding the worst case to ~20MB/hour/user — generous for legitimate iterative publishing, tight enough to matter.
- **[Fixed, medium] Unbounded queries: `SnippetsService`/`PipelinesService.listForOrganization` and `OrganizationsService.getUsage`.** The first two ran a `findMany` with no `take`/cursor, unlike every other list method in this codebase (`list()` on both services caps at `MAX_LIMIT=100`) — reachable by any org MEMBER, a low-cost DoS lever for a large org. Fixed by applying the identical cursor/limit pattern `list()` already uses; both controller routes now accept the same `CursorQuerySchema` query params. `getUsage` had a worse version of the same problem — it pulled every `AiUsageEvent` row for every org member over a 30-day window into Node and reduced them in JS. Rewritten to use Prisma's `groupBy` (`_count`, `_sum`) so the database does the aggregation instead of the application; also added a defensive `MAX_MEMBERS_FOR_USAGE = 500` cap on the member list itself, even though no real organization is close to that yet.
- **[Fixed, low] 403-vs-404 disclosure on private snippets/pipelines.** `SnippetsService.getOne`/`PipelinesService.getOne` returned 403 ("This snippet/pipeline is private") for a resource that exists but the caller can't see, versus 404 for one that doesn't exist at all — letting an authenticated caller enumerate which UUIDs correspond to real (if private) resources. Low real-world impact given UUID keyspace, but inconsistent with `ApiKeysService.revokeKey`'s deliberate "same 404 either way" convention elsewhere in this codebase. Both now return `NotFoundException` for the not-visible case, matching that precedent. API.md §6/§7 updated to describe the unified behavior.
- **[Accepted as a known limitation, not fixed] `PluginRunner`'s 3-second execution timeout doesn't preempt a synchronous infinite loop inside a plugin's WASM.** The timeout only guards against a plugin that never calls back via `postMessage`; it can't interrupt code already blocking the sandboxed iframe's single JS thread. Not a sandbox-escape risk — the opaque-origin/CSP containment (§16.1) still holds regardless — but a reliability concern for a hostile plugin's own execution. The real fix (running the WASM inside a Web Worker *within* the sandboxed frame, so it can be `.terminate()`d from outside) is a legitimate follow-up, not built speculatively in this pass; noted here rather than silently left for someone to discover later.
- **[No action needed — reviewed and confirmed sound]** `effective-plan.ts`'s TEAM-inheritance logic only ever affects the two consumption gates it's meant for, never `/billing/*`; `PluginRunner`'s sandbox correctly omits `allow-same-origin`/`allow-forms`/`allow-popups` and verifies message provenance via `ev.source === iframe.contentWindow` rather than trusting `ev.origin` (which would be the string `"null"` for an opaque origin and therefore useless as a check anyway); `plugins.service.ts`'s admin actions (`review`, `suspend`, `listReviewQueue`) all route through `requireAdmin()` regardless of what the controller's guards allow through, so the metadata-scoping bug above never created a privilege-escalation path even though it did remove rate limiting; org-shared snippet/pipeline creation correctly re-verifies membership before allowing a share, and edit rights are correctly restricted to creator-or-org-admin, not any member; the frontend's client-side `isOwner` check on the plugin detail page is UI-only and correctly re-verified server-side.

### 19.2 Verification

All fixes re-verified in this sandbox after the changes: `npx tsc --noEmit` clean across `backend` and `frontend`; `organizations.service.spec.ts` (14 tests) and `plugins.service.spec.ts` (17 tests) both still pass — `organizations.service.spec.ts`'s usage-aggregation test was updated to mock `aiUsageEvent.groupBy`'s shape instead of `findMany`'s, since the underlying query strategy changed; `plan-throttle.guard.spec.ts` and `api-keys.service.spec.ts` (unaffected by this pass's changes, re-run as a regression check) both still pass.

**Current overall status (end of §19):** Every finding from this pass's security review has been either fixed or explicitly accepted as a documented, non-critical limitation — none were silently dropped. The class-level `@PlanThrottle` bug was the most consequential finding of the whole session: a real gap between documented behavior (API.md's rate-limit tables) and actual enforcement, caught only because a dedicated review pass was run instead of moving straight to the next feature. Worth internalizing as a pattern check for any future controller in this codebase: `@PlanThrottle` must be method-level, never class-level.
